# 网页动效编排手册（操作版）

目标：把「动效」拆成可以照着抄的组件 —— 缓动怎么选、时长给多少、CSS 与 JS 怎么分工、GSAP 怎么编排、要逐帧可复现时怎么锁死时间。每条技法都带 **什么时候用 / 什么时候别用**，代码块可直接粘进页面运行。

约定：
- 所有 `css` 代码示例默认作用在 `.box` 上，先给它固定尺寸和背景色再套用。
- 所有 `js` 示例默认页面已引入 GSAP（`<script src="gsap.min.js">`）或原生 `requestAnimationFrame`。
- 「60fps」= 每帧 16.7ms 预算，这是所有性能判断的基准线。

---

## 0. 选择决策树（先看这张表再往下翻）

| 你的需求 | 首选方案 | 章节 |
|---|---|---|
| hover / press / focus 等状态切换 | CSS `transition` | §4.2 |
| 多关键帧、循环播放（spinner、呼吸、脉冲） | CSS `@keyframes` | §4.3 |
| 列表依次淡入（stagger） | CSS `animation-delay` 或 GSAP `stagger` | §4.4 / §6.5 |
| 需要暂停 / 变速 / 精确 seek / 编排复杂时间线 | GSAP timeline | §6.4 |
| 逐帧可复现渲染（导出视频、截图、回归测试） | GSAP `paused` + `time(t)` 手动推进 | §7 |
| 每帧都要读 DOM / 算物理 | `requestAnimationFrame` | §5 |
| 主线程很忙但动效不能掉帧 | CSS 或 WAAPI（走合成器） | §0 注 / §4 |

> 选择的总原则：**能用 CSS transition 解决的状态切换，就别上 JS 动画。** CSS transition 天然可中断（见 §3.5），而且 `transform` / `opacity` 的 CSS 动画跑在合成器线程，主线程再忙也不掉帧。只有需要「编排、seek、动态计算、逐帧可复现」时才上 JS。

## 1. 缓动（easing）全表

### 1.1 cubic-bezier 的四个参数怎么读

```css
cubic-bezier(x1, y1, x2, y2)
```

一条三次贝塞尔曲线由 4 个控制点决定：起点 `P0(0,0)`、终点 `P3(1,1)` 是固定的，你只能给中间两个控制点 `P1(x1,y1)`、`P2(x2,y2)`。

- **横轴 x = 时间进度**（0 = 开始，1 = 结束），**必须落在 `[0,1]`**，否则该曲线非法。
- **纵轴 y = 输出进度**（属性当前的完成比例），**可以超出 `[0,1]`**。超出就是「过冲」（overshoot），back / bounce 类回弹全靠这一点实现。
- `x1` 越小 → 起步越快（时间轴早期就推进大量进度）。
- `y1 > 1` → 前段冲过终点（回弹/过冲）。
- `x2` 越接近 1 → 尾段越「拖」，减速越晚。
- `y2 < 0` → 前段先倒退（「预备动作」anticipation）。

**什么时候用**：内置关键字不够表达个性（要轻微过冲、要极快起步、要明显拖尾）时手写。
**什么时候别用**：能用 `ease-out` 关键字表达就别手写 —— 关键字可读性更好，队友一眼知道意图。手写 bezier 只用在「关键字做不出、且效果确实需要」的地方。

### 1.2 内置关键字 = 哪个 bezier

| 关键字 | 等价 bezier | 曲线形态 | 感觉 |
|---|---|---|---|
| `linear` | `cubic-bezier(0, 0, 1, 1)` | 一条直线 | 匀速、机械 |
| `ease` | `cubic-bezier(0.25, 0.1, 0.25, 1)` | 起步慢、中段加速猛、尾段缓停 | 通用、略带优雅 |
| `ease-in` | `cubic-bezier(0.42, 0, 1, 1)` | 起步慢、越走越快、末端戛然而止 | 离场、加速离开 |
| `ease-out` | `cubic-bezier(0, 0, 0.58, 1)` | 起步猛、逐渐减速停稳 | 进场、响应、snappy |
| `ease-in-out` | `cubic-bezier(0.42, 0, 0.58, 1)` | 对称 S 形，两头慢中间快 | 位移、A→B |
| `step-start` | `steps(1, jump-start)` | 立刻跳到终值并保持 | 无过渡、闪切 |
| `step-end` | `steps(1, jump-end)` | 保持初值，最后瞬跳终值 | 无过渡、闪切 |

```css
/* 四种关键字各自的等价值，方便你在此基础上微调 */
.a { animation-timing-function: ease; }          /* cubic-bezier(0.25, 0.1, 0.25, 1) */
.b { animation-timing-function: ease-in; }       /* cubic-bezier(0.42, 0, 1, 1)      */
.c { animation-timing-function: ease-out; }      /* cubic-bezier(0, 0, 0.58, 1)      */
.d { animation-timing-function: ease-in-out; }   /* cubic-bezier(0.42, 0, 0.58, 1)   */
```

**什么时候用**：默认起步就用这四个。`ease-out` 覆盖面最广（见 §1.5）。
**什么时候别用**：`ease-in` 单独用在「进场」上会显得犹豫、迟到 —— 进场默认不用 `ease-in`。

### 1.3 back / bounce 的 bezier 写法（elastic 不行）

`back`（回拉）可以用一条 bezier 表达：让 `y` 参数超出 `[0,1]` 制造过冲。

```css
/* easeOutBack：冲过终点再收回来 —— 最常用的“回弹” */
.ease-out-back { animation-timing-function: cubic-bezier(0.34, 1.56, 0.64, 1); }

/* easeInBack：先往回缩一下再冲出去（预备动作） */
.ease-in-back { animation-timing-function: cubic-bezier(0.36, 0, 0.66, -0.56); }

/* easeInOutBack：两头都带一点回弹 */
.ease-in-out-back { animation-timing-function: cubic-bezier(0.68, -0.6, 0.32, 1.6); }
```

`bounce` 与 `elastic` **无法用单条 cubic-bezier 表达**：它们的曲线会多次穿越 `[0,1]` 边界（反弹好几次 / 来回振荡好几轮），而一条三次贝塞尔最多只过一个拐点。要这两种效果只能用 `@keyframes` 手写，或 `linear()`（见 §1.4）。

```css
/* bounce 的经典关键帧：落地三次弹跳 */
@keyframes bounce {
  0%, 20%, 53%, 100% { transform: translateY(0); }
  40%, 43%           { transform: translateY(-30px); }
  70%                { transform: translateY(-15px); }
  90%                { transform: translateY(-4px); }
}
.bounce { animation: bounce 1s cubic-bezier(0.28, 0.84, 0.42, 1); }
```

**什么时候用**：`back` 用在按钮点击、卡片出现、图标强调等「想显得活泼」的地方。
**什么时候别用**：`bounce` / `elastic` 全属于「过量调味」——高频交互（键盘操作、列表 hover）里用会让人烦；一次页面里最多出现一两次。

### 1.4 `linear()` 自定义弹簧曲线（重点）

`linear()` 允许你把曲线拆成任意多个 `(输出值, [位置百分比])` 采样点，浏览器在点之间线性插值。**采样点够密时，可以拟真弹簧、bounce、elastic 这些用手写 bezier 做不到的多段回弹。**

```css
/* 一个“弹簧感”的 linear()：由弹簧生成器采样产出，前段冲过头、反复微振后收稳 */
.spring {
  animation-timing-function: linear(
    0, 0.009, 0.035 2.1%, 0.141, 0.281 6.7%, 0.723 12.9%, 0.938 16.7%,
    1.017, 1.077, 1.121, 1.149 24.3%, 1.159, 1.163, 1.161, 1.154 29.9%,
    1.129 32.8%, 1.051 39.6%, 1.017 43.1%, 0.991, 0.977 51%, 0.974 53.8%,
    0.975 57.1%, 0.997 69.8%, 1.003 76.9%, 1
  );
}
```

语法规则（MDN 规范）：
- 括号里至少给两个值，否则非法。
- 每个值是 `<number>`（输出进度），后面可跟 0~2 个 `<percentage>` 指定它落在时间轴的哪个百分比位置。
- 百分比必须**升序**，否则非法。
- 值必须是数字，`linear(start, middle, end)` 这种写法非法。
- 省略百分比的点会被均分；`linear(0, 0.5 25% 75%, 1)` 等价于 `linear(0, 0.5 25%, 0.5 75%, 1)`。
- **`linear` 关键字永远等于 `linear(0, 1)`**，而写 `linear(0, 1)` 会被解释为 `linear(0 0%, 1 100%)` —— 两者在极边界上的插值行为有差别，别混用。

**浏览器支持（含 2023 后情况）**：

| 浏览器 | 首个支持版本 |
|---|---|
| Chrome / Edge | 113（2023-05） |
| Firefox | 112（2023-04） |
| Safari / iOS Safari | 17.2（2023-12） |
| Opera | 99 |
| Samsung Internet | 23 |

到今天已全绿（Baseline 可用），但**如果要覆盖更老的浏览器**，务必同时给一个 bezier 兜底：

```css
.spring {
  /* 兜底：老的进入者拿到这条 */
  animation-timing-function: cubic-bezier(0.34, 1.56, 0.64, 1);
}
@supports (animation-timing-function: linear(0, 1)) {
  .spring {
    animation-timing-function: linear(/* ...采样点... */);
  }
}
```

**什么时候用**：想用真弹簧的手感、又不想引 JS 动画库时；CSS 里做「果冻」「回弹」「overshoot」的性价比最高方案。
**什么时候别用**：点数一多字符串会长得难看 —— 数据量大、要动态调参（改 stiffness/damping）时用 JS 弹簧（GSAP `elastic` 或 Framer Motion spring）更合适；另外别用它去替代简单的 `ease-out`。

### 1.5 什么时候用哪种缓动（判断规则）

| 场景 | 用哪种 | 理由 |
|---|---|---|
| **元素进场**（出现、弹出、淡入、滑入） | `ease-out` | 起步快 = 立即响应，尾段慢 = 停在目标上显得「到位」。这是覆盖最广的默认。 |
| **元素退场**（关闭、消失、滑出） | `ease-in`（且时长更短） | 慢起快走，让元素「迅速离开」而不是赖着不走。退场容易被忽略，但必须单独设计。 |
| **纯位移 / A→B 移动**（滑轨、指示器切换） | `ease-in-out` | 两头慢中间快，符合物体从静止加速再减速到静止的直觉。 |
| **持续循环**（spinner、进度条、呼吸、脉冲） | `linear` 或 `ease-in-out` | 循环动画首尾要能无缝衔接，`linear` 最稳；要节奏感用 `ease-in-out`。 |
| **物理回弹 / 果冻**（拖拽松手、卡片弹入） | `back` bezier 或 `linear()` 弹簧 | 有质量感的动作需要过冲。 |
| **机械 / 数字跳变 / 逐格** | `steps()` | 需要「一格一格」跳，而不是平滑插值。 |
| **需要断点、非常规节奏** | 手写 `cubic-bezier` | 关键字表达不了时才上。 |

两条硬规则：
1. **进场用 ease-out，退场用 ease-in。** 这是最高频、最不容易错的默认。
2. **同一个动效里，进场的缓动 ≠ 退场的缓动。** 进场「快起慢停」、退场「慢起快走」，是两个方向的设计。

> 「入场容易出场难」的含义：进场动画通常很显眼、容易做对；退场动画经常被敷衍成「直接消失」或「和进场用同一条曲线」，结果拖沓。**退场必须单独给更短的时长 + `ease-in`。**

## 2. 动效时长与延迟的经验值

### 2.1 不同体量元素该用多少毫秒

| 元素体量 | 示例 | 建议时长 |
|---|---|---|
| 微交互 | hover、press、checkbox、tooltip、图标微动 | **100–150ms** |
| 常规控件 | 下拉、开关、tab 高亮、颜色变化 | **150–250ms** |
| 中等容器 | 模态框、抽屉、菜单展开、toast | **200–300ms** |
| 大面积 / 整页 | 页面转场、hero 入场、全屏遮罩 | **300–500ms** |
| 循环 | spinner 单圈、呼吸、脉冲 | **600–1000ms / 圈** |
| 装饰性长动效 | 品牌动画、插画叙事 | 500ms–数秒（仅限非交互、一次性的场景） |

把它写成一组可复用的变量：

```css
:root {
  --dur-fast: 150ms;   /* 微交互 */
  --dur-base: 200ms;   /* 常规控件 */
  --dur-slow: 300ms;   /* 模态、抽屉 */
  --ease-out: cubic-bezier(0, 0, 0.58, 1);
  --ease-in:  cubic-bezier(0.42, 0, 1, 1);
}
.btn:active { transition: transform var(--dur-fast) var(--ease-out); }
.modal      { transition: opacity var(--dur-slow) var(--ease-out); }
```

**什么时候用**：任何交互触发的过渡，都先按这张表取一个值，再微调。
**什么时候别用**：不要给用户高频重复的动作套动画 —— 键盘操作（见 §3.3）一律不加。

### 2.2 为什么超过某个时长会感觉「卡」

要区分两件事：

- **感知上的「拖」**：`duration` 本身太长。经验上限是 **300ms**；一旦超过，动效就不再是「响应反馈」，而变成「需要等待的过程」。尤其对鼠标/键盘触发，用户心理预期是 **100ms 内有响应**。
- **技术上的「卡」（jank）**：单帧渲染耗时 **超过 16.7ms**（60fps 的预算），浏览器掉帧。60fps 下浏览器只有 16.7ms 完成「重算样式 → 布局 → 绘制」整个瀑布；慢脚本或昂贵属性会导致掉帧。

**这两者无关**：一个 150ms 的动画可以因为每帧重排而卡成幻灯片；一个 500ms 的动画也可以丝滑。判断依据不同：
- 觉得「慢」→ 缩短 duration。
- 觉得「卡 / 抖」→ 看属性是不是只动了 transform/opacity（§8.1），看有没有掉帧（DevTools Performance 面板）。

**什么时候用 300ms 上限**：所有交互反馈类动效。
**什么时候别用（可以更长）**：非交互、一次性的品牌/叙事动画；但即便如此，也要保证每一帧都在 16.7ms 内画完。

### 2.3 stagger（依次入场）的合理间隔

| 间隔 | 适用 |
|---|---|
| **20–50ms** | 密集列表、逐字/逐项快速刷出（看起来像「流」而不是「一个个蹦」） |
| **50–100ms** | 卡片网格、菜单项，能清楚分辨先后，又不拖 |
| **100–200ms** | 少量大元素（3–6 个），想要戏剧化的依次登场 |
| **>200ms** | 基本只剩「故意慢放」的叙事场景，交互里几乎不用 |

一个必须记住的公式：

```
总时长 ≈ each × (n − 1) + 单项时长
```

10 个项目、`each = 100ms`、单项 300ms → 总时长 = 100×9 + 300 = **1200ms**，已经超出「一次交互不应超过 ~1s」的红线。

**对策**：项目一多，**别指定 `each`（每项间隔），改指定 `amount`（总错开时间）**。
- CSS：用百分比式 delay，让延迟在固定总窗内分布。
- GSAP：`stagger: { amount: 0.4 }` —— 不管有多少元素，全部错开只花 0.4s。

```css
/* CSS 版：用 min() 给延迟设上限，元素再多总错开也不超过 600ms */
.list-item {
  animation-delay: min(calc(var(--i, 0) * 60ms), 600ms);
}
```

```js
gsap.to(".card", { y: 0, opacity: 1, stagger: { amount: 0.4 } }); // 总错开 0.4s
gsap.to(".card", { y: 0, opacity: 1, stagger: 0.08 });             // 每项错开 0.08s
```

**什么时候用 `each`**：元素少（<8）、想要可预测的固定节奏。
**什么时候用 `amount`**：元素多或数量会变（列表长度不定），用总量控制避免总时长爆炸。

## 3. Emil Kowalski 的动效原则（逐条 + 反例）

方法论优先级最高的一节。下面每条都对应一个「怎么判断该不该做」的决策。

### 3.1 动效必须「自然」

- **原则**：真实世界没有东西瞬间出现或瞬间消失。Web 应用之所以常显得「假」，是因为状态变化是瞬时的。用弹簧（spring）类缓动能让交互更像「活的」，也更好理解。
- **怎么做**：进场用 `ease-out` 或弹簧 `linear()`；有质量感的元素加轻微过冲。
- **反例**：点击后元素「啪」地出现 / 消失，没有任何过渡 —— 用户来不及建立「它从哪来」的空间认知。

### 3.2 动效必须「快」

- **原则**：快速动效提升**感知性能**。两个同样快慢的 spinner，更「用力转」的那个让人觉得加载更好。snappy 的动画让界面显得紧跟用户操作。
- **怎么做**：进场用 `ease-out`（起步快、尾段缓），时长**通常短于 300ms**。
- **反例**：每次打开都要等 500ms 的入场动画 —— 高频使用下会让人抓狂。

### 3.3 动效必须有「目的」，且要考虑「出现频率」

- **原则**：很容易忍不住到处加动画，结果用户被淹没、动画失去冲击力。要在合适的位置加，而不是全加。
- **怎么做**：动画要么**传达信息**（解释流程、指示状态变化，如 modal 的进入/退出、App Store 卡片的切换），要么**强化层级**。加之前先问：用户多久见一次？
- **反例（最典型）**：**永远不要给键盘触发的操作做动画**。这类操作一天可能重复上百次，动画会让它显得迟缓、脱节。一个「每次打开都播 500ms 入场动画」的命令面板是灾难 —— 反例参照 Raycast：**它完全没有动画，反而才对**。

### 3.4 动效必须「高性能」

- **原则**：跑不到 60fps，前面所有努力归零。
- **怎么做**：**只动 `transform` 和 `opacity`** —— 它们只触发渲染瀑布的最后一步（composite），而 `padding` / `margin` / `top` / `left` 会触发全部三步（recalc style → layout → paint）。主线程繁忙时，优先用**硬件加速**的 CSS 动画或 WAAPI，而不是 rAF 驱动的 JS 动画。
- **关键事实**：Framer Motion 之类的库底层用 rAF，**不走硬件加速**。所以元素一多会越来越卡；Vercel 仪表盘的 tab 高亮就栽在这上面（页面加载占满主线程时掉帧），最后改用 **CSS 动画把动画搬到 CPU 之外**才解决。
- **反例**：用 `top` / `left` 做位移动画；主线程满载时用 rAF 动画。

> 注意：硬件加速只对部分属性成立，但只要坚持 `transform` + `opacity`，就安全。

### 3.5 动效必须「可中断」

- **原则**：可中断让动画更自然、更跟手 —— 用户能在任意时刻改变动画方向/目标，且过渡依然平滑。
- **怎么做**：**CSS `transition` 天然可中断** —— 在第一次过渡还没结束时，一个 transition 就能平滑地过渡到新值。用 Framer Motion 则用它内置的可中断能力。
- **反例**：用不可打断的 JS 顺序动画（点开后必须播完才能响应关闭）；用户狂点关闭却发现动画卡在半路。

```css
/* CSS transition 天然可中断：连续改变 width，它会从“当前实际值”接着过渡 */
.meter { width: 20%; transition: width 300ms ease-out; }
.meter.jump { width: 80%; } /* 任何时候切换类，都从当下宽度平滑滑过去 */
```

**什么时候用**：任何用户可以直接反复触发的交互（hover、展开/收起、拖拽）。
**什么时候别用（可以不可中断）**：一次性的、用户无法介入的装饰动画（页面首屏入场），可以放心串行播放。

### 3.6 动效必须「可访问」

- **原则**：对一部分人，动画会**加重不适**（前庭功能障碍者会因动画感到眩晕恶心）或造成分心。必须照顾「不想要动画」的人。
- **怎么做**：用媒体查询降级，或改用 hook 读取偏好。

```css
.element {
  animation: bounce 0.2s;
}

@media (prefers-reduced-motion: reduce) {
  .element {
    /* 不是“全部取消”，而是退回一个更温和的版本：只改透明度，不位移不缩放 */
    animation: fade 0.2s;
  }
}
```

```js
// Framer Motion：用 hook 读偏好，把“位移”降级为“不位移”
import { useReducedMotion, motion } from "framer-motion";

export function Sidebar({ isOpen }) {
  const shouldReduceMotion = useReducedMotion();
  const closedX = shouldReduceMotion ? 0 : "-100%";

  return (
    <motion.div
      animate={{ opacity: isOpen ? 1 : 0, x: isOpen ? 0 : closedX }}
    />
  );
}
```

**什么时候用**：**所有**动效都要过这一关，没有例外。
**什么时候别用「一概不动」的粗暴做法**：正确姿势是「降级」——保留不引起不适的 `opacity` 过渡，去掉位移/缩放/旋转/视差。

### 3.7 缓动曲线要「选得对」——气质一致

- **原则**：缓动和时长要贴合产品整体气质。Emil 的 Sonner（toast 库）之所以讨喜，部分是因为它**特意比常规更慢一点、并用了 `ease` 而不是 `ease-out`**，让 toast 显得更优雅，与它的设计、命名都一致。
- **怎么做**：默认 `ease-out`；想要「优雅 / 沉稳」→ 考虑 `ease` 或更长的时长；想要「干脆 / 响应」→ `ease-out` + 更短时长。这是反复试出来的，需要耐心。
- **反例**：所有动效都无脑套 `ease-out 200ms`，结果整站没有一个动作有性格。

### 3.8 「不要动画 scale(0)」——出场要留一点体积

- **原则**：入场不要从 `scale(0)` 开始。从「零体积」长出来在物理上不成立，看起来像凭空冒出，而且缩放比例跨度太大会显得失真、也更容易在打断时跳变。
- **怎么做**：从 `scale(0.9 ~ 0.96)` 起步，配合 `opacity` 从 0 到 1。缩放跨度小，过渡就更像「轻微放大就位」。

```css
/* 推荐：小跨度缩放 + 淡入 */
@keyframes pop-in {
  from { opacity: 0; transform: scale(0.95); }
  to   { opacity: 1; transform: scale(1); }
}
.pop { animation: pop-in 200ms cubic-bezier(0, 0, 0.58, 1); }
```

```css
/* 反例：从 0 开始 —— 别这么写 */
@keyframes pop-in-bad {
  from { opacity: 0; transform: scale(0); }
  to   { opacity: 1; transform: scale(1); }
}
```

**什么时候可以破例**：确实需要「从无到有」的强表现（一次性品牌动画、图标从点放大），但交互 UI 里默认不用。

### 3.9 动效很「难」，要隔天再看

- **原则**：动效的价值在于「感觉对」，而这只能靠反复试错。Emil 的习惯是**第二天用全新的眼睛重看**，才能发现昨天没注意到的毛刺。
- **怎么做**：把动效 review 当成独立环节，隔一段时间再看一次，而不是写完就收工。

## 4. CSS 动画 vs JS 动画

### 4.1 怎么选

| 维度 | CSS transition / animation | JS（WAAPI / GSAP / rAF） |
|---|---|---|
| 声明方式 | 声明式，写在样式里 | 命令式，写在脚本里 |
| 线程 | `transform`/`opacity` 走合成器，主线程忙也不掉帧 | WAAPI 的 transform/opacity 也走合成器；**GSAP / rAF 走主线程，会掉帧** |
| 可中断 | transition 天然可中断 | 需自行处理（WAAPI/GSAP 支持，裸 rAF 麻烦） |
| 编排复杂时间线 | 弱（靠 `animation-delay` 拼） | 强（GSAP timeline，§6.4） |
| 动态值 / 每帧计算 | 弱 | 强 |
| 精确 seek / 逐帧可复现 | 差（§7.3） | 强（§7.2） |
| 主线程压力下的稳定性 | 好 | 差 |

**判断规则**：
- 状态切换、进出场、单纯位移/透明度 → **CSS**。
- 需要编排、暂停、变速、精确控制时间轴、读 DOM 每帧算 → **JS**。
- 「主线程可能很忙 + 动效不能掉帧」→ **CSS 或 WAAPI**，绝不要用 rAF。

### 4.2 CSS `transition` 骨架（状态切换首选）

```css
.card {
  /* 只声明要过渡的属性，别用 all */
  transition:
    transform var(--dur-base) cubic-bezier(0, 0, 0.58, 1),
    opacity   var(--dur-base) cubic-bezier(0, 0, 0.58, 1);
  transform: translateY(0);
  opacity: 1;
}

.card:hover {
  transform: translateY(-4px);
}

.card.is-hidden {
  opacity: 0;
  transform: translateY(8px);
}
```

要点：
- **列出具体属性，别写 `transition: all`** —— `all` 会把 `width`、`box-shadow` 之类也拖进来，既难预测又容易掉帧。
- transition 写在**基态**（`.card`），这样进入和离开都生效。
- 想加回弹手感，把 timing-function 换成 §1.3 的 back bezier。

```css
/* 回弹版：hover 抬起带一点过冲 */
.card:hover { transform: translateY(-4px) scale(1.02); }
.card { transition: transform 200ms cubic-bezier(0.34, 1.56, 0.64, 1); }
```

**什么时候用**：任何「A 状态 ↔ B 状态」的切换。
**什么时候别用**：需要多段关键帧、需要循环、需要在两个以上状态间平滑接力的复杂编排 —— 换 `@keyframes` 或 GSAP。

### 4.3 CSS `@keyframes` + `animation` 完整语法

```css
@keyframes slide-in {
  from { opacity: 0; transform: translateX(-24px); }
  to   { opacity: 1; transform: translateX(0); }
}

.toast {
  /* 简写：name duration timing-function delay iteration-count direction fill-mode */
  animation: slide-in 300ms cubic-bezier(0, 0, 0.58, 1) 0ms 1 normal both;
}
```

`animation` 各分量：

| 分量 | 值 | 作用 |
|---|---|---|
| `animation-name` | `slide-in` | 引用关键帧 |
| `animation-duration` | `300ms` | 单次时长 |
| `animation-timing-function` | `ease-out` | 缓动（也可写在 keyframe 内，逐段控制） |
| `animation-delay` | `0ms` / `-200ms` | 延迟；**负值 = 立刻从动画中段开始**（seek 技巧，见 §7.3） |
| `animation-iteration-count` | `1` / `infinite` | 次数 |
| `animation-direction` | `normal` / `alternate` / `reverse` | 方向 |
| `animation-fill-mode` | `both` / `forwards` / `backwards` | 动画前后是否保留状态 |
| `animation-play-state` | `running` / `paused` | 暂停（配合 seek 用） |

常用模式：

```css
/* 无限循环 + 来回：呼吸效果 */
@keyframes breathe {
  0%, 100% { transform: scale(1);    opacity: 1; }
  50%      { transform: scale(1.05); opacity: 0.85; }
}
.dot {
  animation: breathe 2s ease-in-out infinite;
}

/* 想暂停/继续：单靠 CSS 就能通过切类控制 */
.paused { animation-play-state: paused; }
```

**什么时候用**：需要多个关键帧、循环、来回往复、或纯 CSS 就够的复杂形态变化。
**什么时候别用**：`fill-mode: forwards` 会把最终样式「钉住」，之后再用 class 改同一个属性会被动画覆盖 —— 需要交接给 JS/状态时注意这一点。

### 4.4 依次淡入（stagger）——靠 `animation-delay`

```css
@keyframes fade-up {
  from { opacity: 0; transform: translateY(12px); }
  to   { opacity: 1; transform: translateY(0); }
}

.list-item {
  opacity: 0;                                  /* 起始不可见，避免闪一下 */
  animation: fade-up 300ms cubic-bezier(0, 0, 0.58, 1) both;
  /* --i 由 HTML 里的 style="--i:0" / 1 / 2 ... 给出 */
  animation-delay: calc(var(--i, 0) * 60ms);
}
```

```html
<ul>
  <li class="list-item" style="--i:0">第一项</li>
  <li class="list-item" style="--i:1">第二项</li>
  <li class="list-item" style="--i:2">第三项</li>
</ul>
```

不想手写 `--i` 也可以用 `nth-child`：

```css
.list-item:nth-child(1) { animation-delay: 0ms; }
.list-item:nth-child(2) { animation-delay: 60ms; }
.list-item:nth-child(3) { animation-delay: 120ms; }
/* ...项一多就得写很多行，所以 --i 方案更适合动态列表 */
```

**什么时候用**：列表/网格初次入场，纯 CSS 就能做，且跑在合成器上不掉帧。
**什么时候别用**：项目数量动态变化且多到几十上百（延迟无法自动收敛，总时长会失控）→ 改用 GSAP `stagger: { amount }`（§6.5）。

### 4.5 JS 动画骨架（WAAPI —— 走合成器的 JS 方案）

当需要 JS 的动态性、又要硬件加速时，用 Web Animations API 而不是手搓 rAF：

```js
const el = document.querySelector(".toast");

const anim = el.animate(
  [
    { opacity: 0, transform: "translateX(-24px)" },
    { opacity: 1, transform: "translateX(0)" },
  ],
  {
    duration: 300,
    easing: "cubic-bezier(0, 0, 0.58, 1)",
    fill: "both",
  }
);

// 可中断 / 可控制：
anim.pause();
anim.currentTime = 150;      // 精确 seek 到 150ms 处（§7.3）
anim.playbackRate = 0.5;     // 半速
anim.reverse();
anim.onfinish = () => console.log("done");
```

**什么时候用**：需要 JS 控制（暂停/seek/变速），但动画属性是 `transform`/`opacity`，希望走合成器。
**什么时候别用**：纯状态切换（CSS transition 更简单）；复杂时间线编排（GSAP 更顺手）。

## 5. `requestAnimationFrame`

### 5.1 正确的循环骨架

```js
let rafId = null;

function frame(timestamp) {
  // timestamp 是浏览器传入的高精度时间，单位 ms，与 performance.now() 同源
  update(timestamp);
  render();
  rafId = requestAnimationFrame(frame); // 递归：下一帧继续
}

// 启动
rafId = requestAnimationFrame(frame);

// 停止
function stop() {
  cancelAnimationFrame(rafId);
  rafId = null;
}
```

三条纪律：
1. **每帧只调一次 `requestAnimationFrame`**，理解成「申请下一帧」，而不是「立刻执行」。
2. 用浏览器**传进来的 `timestamp`** 当时间源，不要在里面另外 `Date.now()`（时间基准会不一致）。
3. 存下返回的 id，停止时用 `cancelAnimationFrame` 取消 —— 它和 `setTimeout` 一样返回一个可取消的句柄。

**为什么比 `setInterval(fn, 1000/60)` 好**：浏览器可以优化它（更同步于渲染）；页面不可见时自动停止（省 CPU、省电）；更省电。

```js
// 反例：不要这么写（时基和渲染不同步，后台还白跑）
setInterval(() => { /* animate */ }, 1000 / 60);
```

**什么时候用**：每帧都要读 DOM / 算物理 / 更新 canvas / 同步多个视觉状态。
**什么时候别用**：只是「A 属性从 0 变到 1」——CSS transition 更快更省。rAF 会占用主线程，主线程一忙就掉帧（§3.4）。

### 5.2 时间差归一化（帧率无关）

不同设备帧率不同（60Hz / 120Hz），如果每帧固定加一个常量，120Hz 设备上的动画会快一倍。必须**按真实经过时间**推进：

```js
let last = null;

function frame(timestamp) {
  if (last === null) last = timestamp;
  const deltaMs = timestamp - last; // 距上一帧的毫秒数
  last = timestamp;

  // 用“每秒 X 单位”的速度，乘上本帧实际经过的秒数
  const deltaSec = deltaMs / 1000;
  state.x += 200 * deltaSec; // 200 单位/秒，帧率无关

  render(state);
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

- **别把 `deltaMs` 无上限地用**：切标签页回来时 `deltaMs` 可能是好几秒，会让物体瞬移出屏。习惯做法是先夹一下：`const dt = Math.min(deltaMs, 50) / 1000;`（50ms ≈ 20fps 以下就按 50ms 算）。
- 需要「相对目标帧率」的缩放系数时，GSAP 提供的 `gsap.ticker.deltaRatio(60)` 就是这个思路（§6.8）。

```js
// 夹住异常大的 delta
const dt = Math.min(timestamp - last, 50) / 1000;
```

**什么时候用**：任何帧率无关的运动（速度驱动的位移、物理模拟）。
**什么时候别用**：如果只是「0 → 1 的插值进度」，直接用 `(now - start) / duration` 算进度，比累加 delta 更不容易累积误差。

### 5.3 与 CSS 动画混用时的同步问题

**坑**：CSS 动画由**浏览器时钟**独立推进，而 rAF 用的是你的 `performance.now()` 时间轴；两者起点不同，且 CSS 动画可能被合成器提前/延后处理。结果是：rAF 里算出的第 N 帧，和 CSS 动画此刻显示的进度**对不上**，逐帧截图里尤其明显。

**原则：一个动效只能有一个时间源。**

- 如果某个元素的节奏必须和其它元素严格对齐 → 全部由 **JS 同一个时间变量**驱动，不要一半 CSS 一半 rAF。
- 想让 WAAPI 动画和 rAF 同步：不要让它自由播放，**关掉自动播放并手动设 `currentTime`**：

```js
// 让 WAAPI 动画跟随你统一的 t（毫秒）
anim.pause();
function frame(t) {
  anim.currentTime = t;      // 用同一个 t 驱动，天然同步
  requestAnimationFrame(frame);
}
```

- CSS 动画**无法被外部时钟精确驱动**，所以需要严格同步时，就把它换成 WAAPI 或直接每帧写 inline style。
- 一个务实的边界：**只有「对齐要求不高」的装饰动画才允许用 CSS 自动播放**（比如某个图标自己转），和主体时间线不要求帧级对齐。

**什么时候用混用**：装饰性、独立节奏的动画（背景呼吸、独立 spinner）。
**什么时候别用**：需要逐帧对齐、需要 seek、需要可复现（§7）—— 一律单一时间源。

## 6. GSAP 核心 API

### 6.1 四个基本方法

```js
// to：从当前状态 → 动画到指定值（最常用）
gsap.to(".box", { x: 200, rotation: 360, duration: 2 });

// from：从指定值 → 动画到当前状态（适合“入场”）
gsap.from(".box", { opacity: 0, y: 40, duration: 1 });

// fromTo：起点和终点都显式给（适合“已知两端”的精确控制）
gsap.fromTo(".box", { x: 0, opacity: 0 }, { x: 200, opacity: 1, duration: 1 });

// set：无动画，立刻设值（等价于 duration 为 0 的 to）
gsap.set(".box", { transformOrigin: "center center", opacity: 0 });
```

`gsap.to(target, vars)` 的组成：**method（方法）+ target（目标）+ vars（配置对象）**。

target 的写法（底层用 `document.querySelectorAll`）：

```js
gsap.to(".box", { x: 200 });                 // 类选择器
gsap.to("#hero", { x: 200 });                // id
gsap.to("section > .box", { x: 200 });       // 复杂选择器
const box = document.querySelector(".box");
gsap.to(box, { x: 200 });                    // 直接传元素
gsap.to([square, circle], { x: 200 });       // 传元素数组
```

**什么时候用 `from`**：入场动画（内容本来就在 DOM 里，只是要「从某处出现」）。
**什么时候别用 `from` 后又 `to` 同一属性**：会得到两段动画，注意起点是「当前值」还是「tween 里写的值」，容易互相打架 —— 两端都明确时用 `fromTo`。

### 6.2 transform 简写对照表

```js
// 这行 CSS：
// transform: rotate(360deg) translateX(10px) translateY(50%);
// 等价的 GSAP 写法：
gsap.to(".box", { rotation: 360, x: 10, yPercent: 50 });
```

| GSAP | 等价的 CSS |
|---|---|
| `x: 100` | `transform: translateX(100px)` |
| `y: 100` | `transform: translateY(100px)` |
| `xPercent: 50` | `transform: translateX(50%)` |
| `yPercent: 50` | `transform: translateY(50%)` |
| `scale: 2` / `scaleX` / `scaleY` | `transform: scale(2)` / `scaleX` / `scaleY` |
| `rotation: 90` | `transform: rotate(90deg)` |
| `rotation: "1.25rad"` | `transform: rotate(1.25rad)` |
| `skew: 30` / `skewX` / `skewY` | `transform: skew(30deg)` / … |
| `transformOrigin: "center 40%"` | `transform-origin: center 40%` |
| `opacity: 0` | 元素的 opacity |
| `autoAlpha: 0` | `opacity` + `visibility` 的组合简写 |

单位与相对值：

```js
gsap.to(".box", {
  x: 200,                       // 默认 px
  y: "+=200",                   // 相对值：在现有基础上再 +200
  z: "40vw",                    // 其它单位，GSAP 会解析
  rotation: "1.25rad",          // 默认 deg，可换 rad
  x: () => window.innerWidth / 2, // 函数值：运行时才算（适合响应式）
});
```

**什么时候用简写**：几乎所有 transform 动画（`x/y` 比手写 `transform` 字符串安全，GSAP 会合并管理各分量，不会互相覆盖）。
**什么时候别用**：需要精确写出一个组合 transform 字符串且不想被 GSAP 拆解时 —— 极少见，默认用简写。

### 6.3 special properties（控制动画行为，不是动画的属性）

| 属性 | 说明 |
|---|---|
| `duration` | 时长（秒），默认 `0.5` |
| `delay` | 开始前延迟（秒） |
| `repeat` | 重复次数；`-1` = 无限 |
| `repeatDelay` | 每次重复之间的延迟 |
| `yoyo` | 每次重复反向播放（像溜溜球），默认 `false` |
| `stagger` | 多目标时各目标启动间隔（秒） |
| `ease` | 缓动，默认 `"power1.out"` |
| `onComplete` | 完成时回调 |

```js
gsap.to(".box", {
  x: 300,
  duration: 1,
  repeat: 2,        // 共播放 3 次（第一次 + 重复 2 次）
  yoyo: true,       // 每次反向往返
  repeatDelay: 0.2,
  ease: "power2.inOut",
  onComplete: () => console.log("done"),
});

// 无限循环
gsap.to(".spinner", { rotation: 360, duration: 1, repeat: -1, ease: "none" });
```

注意 `repeat: -1` 是无限；`repeat: 2` 表示「在此基础上再重复 2 次」，共播 3 次（与 CSS `animation-iteration-count: 3` 对应）。

**什么时候用 `yoyo`**：来回往复（呼吸、摆动、脉冲）。
**什么时候别用 `repeat` + `from`**：`from` 的重复语义容易和直觉不符，往复动画优先用 `fromTo` + `yoyo`。

### 6.4 timeline 与 position 参数（**重点**）

timeline 把多个 tween 串起来统一编排。链式 `.to()` 默认**一个接一个**（默认位置是 `"+=0"`，即「上一个结束处」）。

```js
const tl = gsap.timeline();
tl.to("#green", { duration: 1, x: 1017 })
  .to("#blue",   { duration: 2, x: 1017 })   // 默认：紧接上一个结束后
  .to("#orange", { duration: 1, x: 1017 });
```

**position 参数写在 vars 之后**：`.to(target, vars, position)`。它控制这个 tween 被插到时间轴的哪个位置。全部语义：

| position 写法 | 含义 |
|---|---|
| `3`（数字） | 时间轴上的**绝对时刻**：从 timeline 起点算起的第 3 秒 |
| `"someLabel"` | 插到名为 `someLabel` 的**标签**处（标签不存在会自动加到末尾） |
| `"<"` | 上一个动画的**起点**（`<` 指回上一个动画开头） |
| `">"` | 上一个动画的**终点**（`>` 指向上一个动画结尾） |
| `"+=1"` | 时间轴末尾**再往后 1 秒**（制造间隙） |
| `"-=1"` | 时间轴末尾**往前 1 秒**（与上一个**重叠**） |
| `"<+=3"` / `"<3"` | 上一个动画起点**之后 3 秒**；跟在 `<`/`>` 后面的数字是相对值，`+=` 可省略 |
| `">-0.5"` | 上一个动画结束前 0.5 秒开始 |
| `"myLabel+=2"` | 标签 `myLabel` 之后 2 秒 |
| `"-=25%"` | 以**正在插入的这个动画**总时长的 25% 提前重叠（`+=`/`-=` 后面的百分比基准 = 插入动画自身时长） |
| `"<25%"` | 上一个动画时长的 25% 处（`<`/`>` 后面的百分比基准 = **上一个动画**时长）；`"<25%"` ≡ `">-75%"` |
| `"<+=25%"` | 上一个动画起点之后「插入动画自身时长的 25%」（注意与 `"<25%"` 的基准不同） |

记忆锚点：
- **`<` = 上一个的「头」，`>` = 上一个的「尾」。** 记住这一条就不会用错。
- **`+=` 往后留缝，`-=` 往前重叠。**
- **百分比跟谁：跟 `+=`/`-=` 就是「插入动画」的时长；跟 `<`/`>` 就是「上一个动画」的时长。**（总时长含 repeat/yoyo）
- 这里的「上一个动画」指**最近插入的那个**，不一定是时间轴上最靠后的那个。

```js
let tl = gsap.timeline();

tl.to("#green", { duration: 0.5, x: 1017 })
  .to("#blue",   { duration: 0.5, x: 1017 }, "+=1")   // 缝隙：绿结束后等 1s
  .to("#orange", { duration: 0.5, x: 1017 }, "-=0.25"); // 重叠：提前 0.25s

// 同一时刻并发（多个元素一起动）
tl.to("#a", { x: 100 }, 1)
  .to("#b", { y: 100 }, 1)      // 1s 处，和上一个同起
  .to("#c", { scale: 2 }, "<"); // < = 上一个(b)的起点，也是 1s

// 标签 + 相对标签
tl.add("scene1", 2)
  .to("#x", { duration: 4, x: 200 }, "scene1")
  .to("#y", { duration: 1, opacity: 0 }, "scene1+=3"); // 标签后 3s

// `<0.2` 的实际含义：上一个动画起点之后 0.2s
tl.to("#p", { x: 100, duration: 1 })
  .to("#q", { y: 50, duration: 1 }, "<0.2"); // 与上一个几乎同时起步，仅错开 0.2s
```

**什么时候用 position 参数**：只要涉及两个以上元素需要「错开 / 重叠 / 并发 / 对齐到某一刻」，就该用 timeline，而不是给每个 tween 单独加 `delay`（`delay` 是相对 timeline 起点的绝对延迟，一改前面就全乱）。
**什么时候别用**：只有一个 tween 时 —— 不需要 timeline，直接用 `gsap.to`。

### 6.5 stagger（含 from / axis / ease / grid）

`stagger` 可以是**数字 / 对象 / 函数**三种。

```js
// 数字：每个目标之间间隔 0.1s（负值 = 从最后一个开始往前）
gsap.to(".box", { y: 100, stagger: 0.1 });
gsap.to(".box", { y: 100, stagger: -0.1 }); // 反向
```

对象形式：

```js
gsap.to(".box", {
  duration: 1,
  scale: 0.1,
  yoyo: true,
  repeat: 1,
  ease: "power1.inOut",
  stagger: {
    grid: [5, 13],   // 5 行 13 列：让 GSAP 知道图形排布
    from: "center",  // 从中心向外扩散
    amount: 1        // 全部错开的总时间 = 1s（与 each 二选一）
  }
});
```

| 属性 | 含义 |
|---|---|
| `amount` | **总错开时间**（秒），由所有元素分摊。100 个元素、`amount: 1` → 每个间隔 0.01s。 |
| `each` | **每个元素之间的间隔**（秒）。不管多少元素，间隔固定。**`amount` 与 `each` 二选一。** |
| `from` | 从哪个位置发散：`"start"` / `"center"` / `"end"` / `"edges"` / `"random"`，或某个元素下标（如 `from: 4`）。默认 `0`。 |
| `grid` | 元素排布是网格时给 `[rows, cols]`（如 `[9,15]`）；`grid: "auto"` 用 `getBoundingClientRect()` 自动算（适合响应式，但**只在 stagger 调用那一刻计算**，之后 resize 不会自动重算）。 |
| `axis` | 有 `grid` 时，只按某一条轴计算距离：`"x"` 或 `"y"`。 |
| `ease` | **错开时间本身**的分布曲线。`"power2"` = 前段间隔大、后段越挤越密。默认 `"none"`。 |

函数形式（需要自定义分布时）：

```js
gsap.to(".box", {
  y: 100,
  stagger: function (index, target, list) {
    // 返回“相对起点的总延迟”（不是与上一个的间隔）
    return index * 0.1;
  }
});
```

repeat / yoyo / 回调放的位置决定语义：

```js
// repeat 在顶层：等所有子 tween 都结束后，整体重复
gsap.to(".box", { y: 100, repeat: -1, stagger: 0.1 });

// repeat 在 stagger 对象里：每个元素各自立即重复（错开感持续）
gsap.to(".box", { y: 100, stagger: { each: 0.1, repeat: -1 } });
```

同理，回调（`onUpdate`/`onComplete`/`onStart`）放进 stagger 对象里就是**每个元素各触发一次**。

**什么时候用 `from: "center"` / `"random"` / `"edges"`**：想让动效从某个视觉焦点发散（点击位置、中心、随机散落），比线性扫过更有生命力。
**什么时候别用 `grid: "auto"`**：布局会 resize 时 —— 它只在调用时算一次，resize 后需自己重建（可 `tl.time(0).clear()` 后重新 stagger）。

### 6.6 ease 字符串

GSAP 的 `ease` 用字符串表达，默认 `"power1.out"`。

| 字符串 | 感觉 |
|---|---|
| `"none"` / `"linear"` | 匀速 |
| `"power1"` ~ `"power4"` | 幂次缓动，数字越大越「猛」；`.out` / `.in` / `.inOut` 指定方向 |
| `"power1.out"`（默认） | 快起慢停 —— GSAP 的默认进场手感 |
| `"back"` / `"back.out(1.7)"` | 回拉过冲，括号里是过冲强度 |
| `"elastic"` / `"elastic.out(1, 0.3)"` | 弹簧振荡 |
| `"bounce"` / `"bounce.out"` | 弹跳 |
| `"expo"` / `"expo.out"` | 指数级缓动，起步/收尾极陡 |
| `"steps(5)"` | 逐格跳变 |
| `"rough"` / `"slow"` | 粗糙 / 慢速的趣味预设 |

```js
gsap.to(".box", { x: 300, ease: "power2.out" });        // 常规进场
gsap.to(".box", { scale: 1.2, ease: "back.out(2)" });   // 明显回弹
gsap.to(".box", { y: 0, ease: "elastic.out(1, 0.4)" }); // 弹簧落定
gsap.to(".box", { x: 300, ease: "none" });              // 匀速（循环用）
```

**什么时候用**：`.out` 用于进场（快起慢停），`"none"` 用于无限循环，`back`/`elastic` 用于回弹强调。
**什么时候别用**：`elastic` / `rough` 属于强调味，交互里慎用；默认 `power1.out` 已经适用于大多数进出场，别一上来就上弹跳。

### 6.7 `gsap.registerPlugin`

插件（ScrollTrigger、Draggable、MorphSVG 等）必须先注册才能用：

```js
gsap.registerPlugin(ScrollTrigger);

gsap.to(".panel", {
  x: 300,
  scrollTrigger: { trigger: ".panel", start: "top center", scrub: true }
});
```

**什么时候用**：引入任何 GSAP 插件时，在**动效创建之前**调用一次。
**什么时候别用**：只用核心 API（to/from/timeline）时不需要，别为了「保险」而注册不用的插件。

### 6.8 `gsap.ticker` 与「手动推进」的关系

`gsap.ticker` 是 GSAP 引擎的**心跳**：它在**每个 `requestAnimationFrame`** 上更新 `gsap.globalTimeline`，所以和浏览器渲染周期天然同步。所有 tween / timeline / delayedCall 都由**这一个**时间机制驱动。

```js
// 加监听（每 tick 在引擎更新之后执行）
gsap.ticker.add(myFunction);
function myFunction(time, deltaTime, frame) {
  // time      : 自 ticker 启动以来的总秒数
  // deltaTime : 距上一次 tick 的毫秒数
  // frame     : 帧计数
}
gsap.ticker.remove(myFunction); // 移除

// 只在下一帧执行一次，且排在 globalTimeline 之前
gsap.ticker.add(myCallback, true, true); // (fn, once, prioritize)
```

相关的三个实用接口：

```js
gsap.ticker.fps(30);                    // 把 ticker 限到 30fps（只能低于原生帧率）
gsap.ticker.deltaRatio(60);             // 相对 60fps 的时长比例，用于帧率无关的手动更新
gsap.ticker.lagSmoothing(500, 33);      // 默认值：单次卡顿 >500ms 时，按只过了 33ms 处理
gsap.ticker.lagSmoothing(0);            // 关闭 lag 平滑
```

- **`lagSmoothing` 的意义**：CPU 卡顿时，多数引擎会把起始时间往后推（保住真实时长、丢掉同步），GSAP 则**坚持严格时间模型保住同步**。默认 `(500, 33)` 是折中：只有单次掉帧超过 500ms 才把内部时钟按 33ms 推进一格，从而所有动画仍保持同步。想「时间被完全锁死、绝不能自我修正」时（确定性渲染，§7）应关闭它。
- **`deltaRatio(fps)`**：`obj.x += 3 * gsap.ticker.deltaRatio(60)` 可让速度在帧率波动下保持一致。

**手动推进（"手动 advance"）**：ticker 是「自动」推进 —— 每帧按真实时间往前走。如果你想**自己决定时间轴走到哪一秒**，就要把动画设为 `paused`，用 `time()` 手动设播放头：

```js
const tl = gsap.timeline({ paused: true }); // 关掉自动播放
tl.to(".box", { x: 300, duration: 1 })
  .to(".box", { rotation: 360, duration: 1 });

tl.time(0);    // 渲染第 0 秒的画面
tl.time(0.5);  // 渲染第 0.5 秒的画面（精确 seek）
tl.time(1.5);  // 渲染第 1.5 秒的画面
```

`time()` 与 `totalTime()` 的区别：`time` 是**局部播放头**，不含 repeat/repeatDelay（有 repeat 时它会回到 0 重新计），`totalTime` 是含重复的**总时间**。手动 seek 一般用 `time()`。

**什么时候用 ticker 自动推进**：所有常规交互动效。
**什么时候用手动 advance**：需要逐帧可复现渲染时 —— 见 §7。

## 7. 确定性动画（逐帧可重复渲染）

**要求**：同一个时间点 `t` 渲染出的画面，每次运行都必须**完全一致**。用于导出视频、逐帧截图、视觉回归测试、离线渲染。做不到这点，出片就会「每次都不一样」。

### 7.1 时间源禁忌：不许有「随机的现在」

要可复现，画面就必须是**纯函数**：`frame = f(t, seed)`，`f` 里不能有任何每次运行都不同的输入。

| 禁止 | 为什么 | 替代 |
|---|---|---|
| `Date.now()` / `new Date()` | 每次运行值不同 | 用固定推进的 `t` |
| `performance.now()` 当动画时间 | 依赖真实运行速度，掉帧就变 | 手动推进的帧号 / 固定 fps |
| `Math.random()` | 每次序列不同 | **固定种子的伪随机**（下例） |
| 依赖 `requestAnimationFrame` 的真实节奏 | 掉帧/lagSmoothing 会让同一 `t` 得到不同画面 | 关掉自动播放，手动 `time(t)` |
| 实时网络/异步数据 | 完成时刻不定 | 先 await 数据，再开始渲染 |
| 外部可变状态（滚动位置、鼠标） | 每次不同 | 快照成固定常量，或排除出动画 |

固定种子的伪随机（mulberry32），保证「随机」也每次一样：

```js
function mulberry32(seed) {
  return function () {
    seed |= 0; seed = (seed + 0x6D2B79F5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
const rand = mulberry32(12345);   // 同一个种子 → 同一个序列
```

**什么时候用**：只要产出物要被复用/对比（视频、截图、CI 快照），一律用固定种子。
**什么时候别用**：真实交互里想要「每次略不同」的自然感时，可以用真随机 —— 但那就别声称可复现。

### 7.2 标准做法：`paused` timeline + 固定 fps 手动 `time(t)`

骨架：**先构建好整条时间线并暂停，然后按固定 fps 逐帧设 `time()` 并截图。**

```js
const FPS = 30;                    // 固定帧率（不要用真实 rAF 的帧率）
const DURATION = 4;                // 时间线总长（秒）
const TOTAL_FRAMES = FPS * DURATION;

// 1) 构建动画，pause 掉自动播放
const tl = gsap.timeline({ paused: true });
tl.to(".box", { x: 300, duration: 1, ease: "power2.out" })
  .to(".box", { rotation: 360, duration: 2, ease: "none" }, "+=0.5")
  .to(".box", { scale: 1.5, duration: 1.5, ease: "back.out(1.6)" }, "<");

// 2) 关闭所有会“自我修正”的机制，保证时间完全由我们决定
gsap.ticker.lagSmoothing(0);
gsap.ticker.fps(FPS);              // 可选：让 ticker 也按固定节奏（但关键还是手动 time）

// 3) 逐帧渲染：t = frame / FPS，完全确定
for (let frame = 0; frame <= TOTAL_FRAMES; frame++) {
  const t = frame / FPS;           // 第 N 帧对应的时间点
  tl.time(t);                      // 精确 seek，同步渲染这一帧
  // 这里做截图 / 导出 / 比较
  // captureFrame(frame);
}
```

关键点：
- **`paused: true`**：必须。否则 ticker 会自己往前推，`time()` 设的值立刻被覆盖。
- **`t = frame / FPS`**：时间是「帧号算出来的」，不是「等出来的」——所以第 300 帧在任何机器上都是第 10.0 秒。
- **`gsap.ticker.lagSmoothing(0)`**：关掉掉帧补偿，时间只由我们说了算。
- **`suppressEvents`**：如果不想在 seek 过程中触发回调，用 `tl.time(t, true)`（第二个参数 suppressEvents）。

**别做的事**：不要用「每帧 `requestAnimationFrame` + 累积真实 delta」来做可复现渲染 —— 真实 delta 每次运行都不同。

**什么时候用**：导出成片、逐帧截图、自动化视觉测试。
**什么时候别用（没必要）**：普通网站上用户直接观看的动效，让它按真实时间播放更自然、也更简单。

### 7.3 CSS 动画在逐帧截图下的坑

**核心问题**：CSS 动画由浏览器自己的时钟推进，**你无法给它一个精确的 `t`**。于是：

- 你在第 N 帧截图时，CSS 动画实际显示在哪一步，取决于它「从开始到现在真实过了多久」——受掉帧、合成器调度影响，**不确定**。
- 想「暂停在某时刻」只有一个近似技巧：`animation-play-state: paused` 配合**负 `animation-delay`** 把播放头推到某处：

```css
/* 近似 seek：暂停 + 负 delay 把播放头往后推 500ms */
.seek-500ms {
  animation-play-state: paused;
  animation-delay: -500ms;
}
```

但这个技巧**不精确**：不同浏览器对负 delay + paused 的组合处理不完全一致，且它无法做到「同一帧号必得同一画面」的严格保证。

**结论**：
- 需要逐帧可复现 → **不要用 CSS 自动播放的动画**。
- 把需要可控的动画换成 **WAAPI**（`anim.pause(); anim.currentTime = t;` 是精确 seek）或 **GSAP 手动 advance**（§7.2）。
- 如果某个副作用只能用 CSS，就把它彻底排除出「需要复现」的范围（比如禁用该装饰动画）。

**什么时候用负 delay 技巧**：只是想给用户「停在某个状态」的展示（静态预览某进度），不要求帧级复现。
**什么时候别用**：任何需要「同一 t → 同一像素」的渲染管线。

### 7.4 为什么 HMR / 热重载会毁掉长时间渲染

热重载（HMR / dev server 的即时重载）会：

- **重建模块**：`tl` 被重新创建、`time()` 归零，动画从头开始 —— 渲染到一半时依赖它，画面会跳回起点。
- **重复注册副作用**：`gsap.ticker.add(...)`、事件监听被再加一遍，导致回调重复执行（帧被算两次、速度翻倍）。
- **重跑初始化**：固定 seed 如果写在模块顶层，重载可能重新播种；若 seed 来自 `Date.now()` 之类，序列直接改变。
- **注入样式/替换节点**：DOM 被替换掉，已捕获的元素引用失效，动画作用到脱离文档的旧节点上。
- **时序不确定**：重载发生在什么时候不确定，会污染「第几帧」。

**对策**：
- 渲染任务跑在**构建后的产物**上（`npm run build` 后启动），不要跑在开着 HMR 的 dev server 上。
- 必须用 dev server 时：**关掉 HMR**（如 Vite 的 `server.hmr: false`）。
- 在渲染入口做**清理 + 单例**：每次初始化前 `gsap.killTweensOf("*"); gsap.globalTimeline.clear();`，并保证初始化只执行一次。
- 固定 seed 用**常量**，不要从时间/随机源取。
- 等**资源就绪**再开始：`await document.fonts.ready;` 和图片 `decode()`，否则首帧会因字体/图片未加载而与后续运行不一致。

```js
// 渲染入口的确定性初始化骨架
async function renderDeterministically() {
  await document.fonts.ready;                 // 字体就绪
  await Promise.all(
    [...document.images].map((img) => img.decode())
  );                                          // 图片就绪
  gsap.killTweensOf("*");                     // 清掉旧实例（防 HMR 重复）
  gsap.globalTimeline.clear();
  gsap.ticker.lagSmoothing(0);

  const rand = mulberry32(12345);             // 常量 seed
  const tl = buildTimeline(rand);             // 用固定 seed 构建，paused:true
  for (let f = 0; f <= FPS * DURATION; f++) {
    tl.time(f / FPS);
    await captureFrame(f);
  }
}
```

**什么时候必须这么做**：任何「渲染一次、要用很久」的非交互产出。
**什么时候可以忽略**：普通开发中的交互页面，HMR 重载反而方便；只是别指望在它上面做可复现导出。

## 8. 性能清单

### 8.1 只动 `transform` / `opacity`

渲染瀑布是三步：**recalculate style → layout → paint**（paint 之后还有 composition）。

| 属性类型 | 触发 | 例子 |
|---|---|---|
| 影响几何/位置 | recalc style + **layout** + paint | `left`、`top`、`width`、`max-width`、`border-width`、`margin-left`、`font-size` |
| 不影响几何、未独立成层 | recalc style + paint | `color`、`background-color` |
| 独立成层（合成） | 仅 recalc style | **`transform`、`opacity`** |

```css
/* 好：只走 composite */
.move { transition: transform 200ms ease-out; }
.move.active { transform: translateX(120px); }

/* 差：每帧触发 layout + paint */
.move-bad { transition: left 200ms ease-out; }
.move-bad.active { left: 120px; }
```

**什么时候用**：所有动效的位置/缩放/旋转/透明度。
**什么时候别用（例外）**：确实需要动 `height`（如展开收起）时，优先改成 `transform: scaleY()` + `transform-origin` 的近似（注意会拉伸内容），或用 `grid-template-rows: 0fr → 1fr` 这类现代方案；实在要用真 `height`，就接受它不是合成层动画。

### 8.2 `will-change` 的用法与滥用

`will-change` 提前告诉浏览器「这个元素将要变」，让它**提前建合成层**、避免起始抖动。

```css
/* 正确：在动画真正发生前加，动画结束后移除 */
.card { transition: transform 200ms ease-out; }
.card:hover { will-change: transform; }        /* 悬停即将变换时提示 */

/* 或者用 class 在动画期间挂上 */
.is-animating { will-change: transform, opacity; }
```

```js
// JS 侧：加上 → 动画 → 结束后移除，避免长期占用
el.style.willChange = "transform";
gsap.to(el, {
  x: 300,
  onComplete: () => { el.style.willChange = "auto"; }
});
```

**什么时候用**：动画即将开始的一小段时间；动画确实会掉帧且确认是合成层未提前建立导致时。
**什么时候别用（滥用）**：
- **不要全局无脑加** `will-change: transform`。每个 `will-change` 都会占内存、可能生成新层，元素一多就是「层爆炸」，反而拖慢合成、吃显存。
- 不要为了「优化」给静态元素常驻 `will-change`。浏览器自己的优化已经够好，滥用会适得其反。

### 8.3 `contain`（限制影响范围）

`contain` 告诉浏览器「这个子树的变化不会影响外面」，让它跳过无关的重排/重绘判断。

```css
.card {
  contain: layout paint;   /* 该元素的布局与绘制不影响外部 */
}
.widget {
  contain: strict;         /* = size layout style paint，最激进 */
}
```

常用值：`layout`（内部布局不影响外部）、`paint`（绘制被裁剪到本元素内）、`size`（元素尺寸不受内部影响）、`style`、`strict`（前四者全开）。

**什么时候用**：列表中大量独立卡片/组件、长列表项 —— 每个 item 加 `contain: layout paint` 能明显降低整体重排成本。
**什么时候别用**：`contain: paint` 会**裁剪溢出内容**并让元素成为包含块，可能改变 `position: absolute` 子元素的定位基准 —— 有溢出或绝对定位子元素时慎用；`contain: size` 要求元素尺寸不依赖内容，乱用会让尺寸塌掉。

### 8.4 避免 layout thrashing（读写交替）

**问题**：先读一个会触发布局的属性（`offsetWidth`/`getBoundingClientRect`/`scrollTop`），再写一个几何属性，再读 —— 每次「写后读」都会强制浏览器**立刻重新布局**，一帧里反复几次就掉帧。

```js
// 反例：读 → 写 → 读 → 写 …… 每轮都强制布局
for (const el of items) {
  const h = el.offsetHeight;          // 读（触发 layout）
  el.style.height = h + 10 + "px";    // 写（让布局失效）
  const w = el.offsetWidth;           // 又读 → 强制重新 layout
  el.style.width = w + "px";
}
```

```js
// 正例：先全部读，再全部写
const sizes = items.map((el) => ({
  h: el.offsetHeight,
  w: el.offsetWidth,
}));                                   // 阶段一：只读
items.forEach((el, i) => {
  el.style.height = sizes[i].h + 10 + "px";
  el.style.width = sizes[i].w + "px";
});                                    // 阶段二：只写
```

**FLIP（First-Last-Invert-Play）** 是把「位移」从布局属性搬到 transform 的标准手法：先量首尾位置，用 transform 反着摆回起点，再过渡到终点 —— 全程只动 transform。

**什么时候用**：一帧内要批量处理多个元素的几何信息。
**什么时候别用（不那么重要）**：只读一次或只写一次的场景 —— 过度设计批处理反而让代码难读。

### 8.5 合成层（compositor layer）的建立条件

当一个元素「独立成层」，对它的 `transform`/`opacity` 变化就只需要 **composition**，不再重绘 —— 这是 60fps 的关键。

常见的促成层条件（各浏览器判定不同，以下是常见触发）：
- `transform` 含 3D 值：`translateZ(0)` / `translate3d(...)` / `rotate3d(...)`
- `will-change: transform` / `will-change: opacity`
- `opacity` 小于 1 且参与动画
- `filter`、`backdrop-filter`
- `position: fixed`
- `<video>`、`<canvas>`、`<iframe>`
- 3D 上下文中的 `backface-visibility: hidden`
- 元素正在被动画（浏览器可能在动画期间自动提升）

```css
/* 手动促层（慎用，别到处加） */
.lifted { transform: translateZ(0); }
```

**什么时候用**：一个大面积元素要做高频动画、确认掉帧时；用 DevTools 的 Layers / Rendering 面板确认层确实建起来了。
**什么时候别用（重要）**：
- **层不是越多越好**。每个层都吃显存、增加合成开销，元素一多反而更卡（「层爆炸」）。
- 别用 `translateZ(0)` 给全站元素「提速」，只在你确认需要且测出收益时用。

### 8.6 `prefers-reduced-motion`

```css
/* 全局降级：对开启“减少动态效果”的用户，压缩所有动效时长 */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

```css
/* 更讲究的做法：只保留“不引起不适”的属性（透明度），去掉位移/缩放 */
@media (prefers-reduced-motion: reduce) {
  .slide-in {
    animation: fade-in 150ms linear both;   /* 位移版 → 淡入版 */
  }
}
```

```js
// JS 侧读偏好
const reduce = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
gsap.to(".card", { y: reduce ? 0 : 40, opacity: 1, duration: 0.3 });
```

**什么时候用**：**全站所有动效**，这是可访问性底线（§3.6）。
**什么时候别用「全灭」**：不要简单粗暴地把一切动画都杀掉 —— 一些动效承担了「指示状态变化」的信息功能（如 modal 进出），把它降级成淡入而不是直接消失，信息才不丢失。

## 9. 落地清单（做动效时逐条自检）

- [ ] 这个动效**有目的**吗？它传达信息/状态变化，还是纯粹炫技？
- [ ] 用户**多久见一次**？高频（尤其键盘触发）→ 不加或极短。
- [ ] 进场用 `ease-out`、退场用 `ease-in`、位移用 `ease-in-out`？
- [ ] 时长是否 **≤300ms**（交互类）？有没有按元素体量分档？
- [ ] 是不是**只动** `transform` / `opacity`？
- [ ] **可中断**吗？（CSS transition 默认可以；JS 顺序动画要确认能被打断）
- [ ] 有没有照顾 `prefers-reduced-motion`？（是降级，不是删除）
- [ ] stagger 用 `each` 还是 `amount`？总时长会不会超 1s？
- [ ] 多个元素需要错开/对齐 → 用 **timeline + position 参数**，而不是各自 `delay`？
- [ ] 要**逐帧可复现**吗？→ `paused` timeline + `time(t)`，无 `Math.random`/`Date.now`，关 lagSmoothing，跑在无 HMR 的构建产物上。
- [ ] `will-change` / 层提升是否**用完就撤**，没有全站滥用？
- [ ] `contain` 有溢出/绝对定位子元素的风险吗？
- [ ] 有没有在同一帧里读写交替（layout thrashing）？
